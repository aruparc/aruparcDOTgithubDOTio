Voice Chat Moderator: Helping Moderators Focus

A moderation team needs to identify harmful speech without losing the context of a conversation. I built this prototype to explore how audio clips could become reviewable recommendations, with uncertain cases handed to a person.

The Problem & Project Goals

Voice conversations are difficult to review because the words alone may not tell the whole story. A phrase can be gameplay banter, a quotation, or a targeted threat depending on the surrounding conversation. A useful assistant needs a way to look for that context and recognize when it still does not have enough information.

My goal was to connect audio input to a moderation recommendation that someone could inspect. For a community team, the intended value is less effort assembling evidence and a clearer path for reviewing uncertain cases. This is a prototype of that workflow; reduced review time and moderation accuracy still need to be measured.

From Audio Processing to an Agent

There are four layers to the current design. They show how a straightforward audio pipeline becomes a system that can gather evidence and support a human decision.

01

Make speech readable

The simplest layer accepts a recording or upload, normalizes its audio format, and sends it to the backend. FastAPI waits for the completed clip and selects either local Whisper transcription or the Gemini Live transcription path. Keeping that transport predictable gives the moderation layer a consistent text input.

02

Produce a structured recommendation

The next layer asks a moderation model to choose allow, flag, or escalate. The result includes categories, confidence, an explanation, and quoted evidence where applicable. Runtime validation requires a policy category and observed evidence before accepting a flag. A quote match helps prevent invented evidence, but does not prove that the interpretation is correct.

03

Let the model gather context

A more complex case may need earlier speech or a closer look at policy. The model can select tools, receive their results, and reconsider its next action. It does not have to follow a fixed sequence of lookups. The same loop works with Ollama or Gemini, independently of the transcription provider.

04

Keep a record and involve a person

SQLite stores clips, recommendations, tool observations, and review cases. Escalations appear in a session review queue where a person can record a decision and note. That resolution is kept separately from the original recommendation, preserving what the agent suggested and what the reviewer decided.

How the System Is Orchestrated

I separated audio orchestration from moderation decisions. The orchestrator handles the path from bytes to a transcript. The moderation agent then chooses what information it needs before finishing with a recommendation or a review request.

The frontend and backend have separate Docker images. Compose keeps the API on its internal network and persists the moderation database and Whisper model cache in named volumes. This makes the prototype easier to run repeatedly without treating each launch as a fresh session.

What the agent can actually do

lookup_moderation_policy
Retrieve guidance for one category or all categories, such as harassment, threats, or disclosure of personal information.
get_recent_player_context
Read up to 20 earlier clips in the current session, optionally narrowed to a speaker. The current clip is excluded.
get_session_behavior
Inspect a player's last 100 recommendations in this session. Previous recommendations are not confirmed violations.
record_moderation_event
Finish with a validated allow, flag, or escalate recommendation. An escalation also creates a review entry.
request_human_review
Finish by queuing an uncertain or urgent case for a person.

For example, an ambiguous gameplay phrase could lead the model to retrieve earlier clips, consult the threats policy, and then decide whether to allow it or request review. That is an illustrative path, not a guaranteed sequence or a measured test result. The model can also finish a clear case immediately.

Results & What I Learned

The implemented result is a connected workflow: submit a clip, transcribe it, run a bounded moderation loop, inspect the tool trace, and resolve an escalation through the review queue. The repository supports those capabilities, but does not provide an accuracy benchmark or evidence of reduced moderator workload.

The key design lesson for me is that a moderation assistant needs a defined way to stop. Invalid tool arguments become observations the model can correct. A valid terminal tool ends the loop. If the agent reaches its turn, tool, or time budget, the system creates a human review case. This makes unresolved decisions visible instead of leaving the workflow open-ended.

Where the prototype stops

The app recommends actions; it does not mute or ban players. Its context comes from submitted clips in the same session, with no live game telemetry. Review endpoints have no reviewer authentication, and session IDs organize records rather than authorize access. These constraints matter before moving from a local demonstration to a shared service.

What I would evaluate next

I would build a labeled set of clips covering clear violations, ordinary banter, quoted speech, and missing context. I would measure false positives, missed violations, escalation frequency, and end-to-end latency, then compare the local and hosted provider paths. Reviewer agreement and time per case would help determine whether the extra orchestration actually makes moderation work easier.

Before a shared pilot, I would also add reviewer authentication, define transcript retention, and evaluate simultaneous sessions. Continuous audio ingestion would be a separate extension of the current completed-clip workflow.

Implementation: audio orchestrator, bounded agent loop, validated tools, and workflow documentation.
