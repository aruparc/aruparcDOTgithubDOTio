Document Chat: Simplifying Dense Documents by Leveraging RAG

Finding an answer in a long document can take longer than acting on it. This project explores how a team could spend less time manually searching through files and more time using the information inside them.

The Problem

A collection of documents can contain exactly what someone needs and still be tedious to navigate. A keyword search helps when the reader already knows the right words, but often still requires some manual sifting of information in the source document(s). For a support or operations team, that perpetuates manual work every time someone has to locate and interpret information in a bulk of documents.

The goal of this project was to make that interaction simpler: upload one or more documents, ask questions in everyday language, receive accurate information, and ask follow-up questions without starting over.

Why not use just ChatGPT, Gemini, or Claude etc.? The business value here is two fold: freedom to customize the user experience, and data privacy. Many times, teams and organizations will work with documents and data that should not be exposed to external providers. By self-hosting and owning the RAG platform, they protect their data, information, and freedom to customize the experience with UI and model changes.

The User Experience: From File Upload to a Conversation

The system is easiest to understand in three layers. Each layer adds a capability that the previous one cannot provide on its own.

01

Upload documents

Before asking a model anything, users upload their documents. The app accepts PDF, DOCX, or TXT files, extracts its text, and previews the first few chunks.

02

Extract, chunk, vectorize

Next, the text is split into 500-character chunks with a 50-character overlap. The overlap helps preserve context across boundaries. An embedding model converts those chunks into vectors, which gets stored locally in ChromaDB alongside the original text, filename, document ID, and chunk index. A user's question goes through the same embedding model so the app can retrieve five related passages.

03

Facilitate conversations with appropriate context

Retrieved passages and up to four recent conversation turns are passed to the local language model with every new user prompt. The allows the LLM to use document context as evidence, use chat history to understand references, and respond to user requests. Finally, the system will acknowledge when an answer cannot be determined.

System Design: How the Pieces Work Together

Ollama supplies both the nomic-embed-text embeddings and the llama3.2:3b chat model. The chat client uses an OpenAI-compatible interface pointed at localhost. Chroma persists the collection on disk, while the conversation lives in Streamlit session state.

One useful tradeoff became clear in the implementation: persistence makes earlier uploads available again, but the current query searches the whole collection. There is no selected-document filter or duplicate-upload check. Those controls would matter if a team used this with many documents.

Results & What I Learned

The repository includes a timing log from a Honda Integra document experiment on September 21, 2026. It gives a concrete view of the prototype's latency, although it does not include a scored answer-quality evaluation.

Recorded prototype timings · one local experiment
OperationRecorded time
Extract text from PDF0.939 seconds
Split text into chunks0.002 seconds
Generate embeddings and store chunks17.529 seconds
Ask for five facts about the Honda Integra91.782 seconds
Follow up on engines and years of operation121.714 seconds

The response timer covers question embedding, retrieval, prompt construction, and generation. These are individual observations, not averages or a production benchmark. The log does not establish answer accuracy or hardware-normalized performance.

What stood out to me was how little time text splitting took compared with waiting for an answer. A useful document assistant needs to be both grounded and responsive; this experiment identifies response latency as an important area to investigate before claiming a productivity improvement.

Scaling Beyond

Some ways to build on top of this current implementation:

- Add more LLM options
- Add model guardrails, customization options for model hyperparameters (temperature, top-p, top-k, frequency penalty, presence penalty, etc.)
- Token usage logging (input and output tokens)
